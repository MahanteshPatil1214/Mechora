# 1. Product Vision

MECHORA is an AI-assisted safety intelligence platform that transforms unstructured safety observations into structured safety events and identifies recurring **precursor mechanisms and barrier failures** across apparently different incidents.

The central product principle is:

> **We don't cluster stories. We cluster safety mechanisms.**

Instead of treating every safety observation as an isolated report, MECHORA identifies the underlying combination of:

**Activity → Hazard/Energy → Required Barrier → Barrier State → Exposure → Potential Consequence**

This enables HSE teams to discover recurring precursor mechanisms that may remain hidden when reports are reviewed individually.

---

# 2. Problem Definition

Large organizations generate significant volumes of:

* Unsafe Act (UA) observations
* Unsafe Condition (UC) observations
* Near-miss reports
* Incident reports
* Safety observations

These reports frequently contain valuable information in free-text form.

However, manual or periodic review creates several challenges:

1. Large volumes make continuous analysis difficult.
2. Low-severity observations may receive less attention despite potentially serious exposure mechanisms.
3. Similar safety mechanisms may appear under completely different wording.
4. Different equipment or activities may hide the fact that the same critical barrier is repeatedly failing.
5. Existing NLP approaches may identify textual similarity without adequately identifying the underlying safety mechanism.
6. HSE teams need explainable evidence rather than opaque AI classifications.

The product therefore focuses on moving from:

**Individual Report Intelligence**

to:

**Recurring Precursor Intelligence.**

# 7. Functional Requirements

## FR-01 — Observation Submission

The system shall allow a user to submit a free-text safety observation.

### Input

```text
Narrative
```

### Output

A unique observation record.

---

# FR-02 — Structured Extraction

The system shall extract structured safety attributes from the narrative.

The extraction response must conform to a predefined JSON schema.

The system must reject or flag malformed AI output.

---

# FR-03 — Evidence Linking

Every important extracted safety attribute should, where possible, retain evidence from the original narrative.

Example:

```json
{
  "attribute": "barrier_state",
  "value": "not_verified",
  "evidence": "before confirming zero pressure"
}
```

---

# FR-04 — Negation Handling

The system must detect safety-critical negation.

Examples:

```text
Isolation verified
```

≠

```text
Isolation NOT verified
```

---

# FR-05 — Canonical Normalization

Different terminology should map to common concepts.

Examples:

```text
zero pressure confirmed
depressurized
pressure released
zero-energy state verified
```

may map to relevant canonical concepts.

Normalization must not remove meaningful distinctions.

---

# FR-06 — Precursor Signature

The system shall generate a normalized structural signature for every observation.

---

# FR-07 — Structural Similarity

The system shall calculate similarity between safety events using structural dimensions.

Text embeddings may be used as a supporting signal but must not be the sole basis for precursor grouping.

---

# FR-08 — Precursor Family

The system shall group structurally similar observations into precursor families.

Each family should have:

* unique ID
* generated name
* common hazard/energy
* common barrier
* common barrier failure
* common exposure
* affected activities
* affected locations
* supporting observations

---

# FR-09 — SIF Assessment

The system shall provide:

* SIF-potential assessment
* confidence
* supporting evidence
* reason/explanation

The product must not claim certainty.

---

# FR-10 — Life-Saving Rule Mapping

The system shall identify relevant Life-Saving Rule(s) where sufficient evidence exists.

If confidence is insufficient:

```text
Needs HSE Review
```

rather than forcing a classification.

---

# FR-11 — HSE Attention Signal

The system may calculate a prototype precursor attention signal based on factors such as:

* recurrence
* barrier failure frequency
* exposure characteristics
* cross-activity occurrence
* SIF-potential observations

This must be clearly labelled as a **prototype attention signal**, not an official OIL risk score.

---

# FR-12 — Explainability

For every major AI-derived result, the system should provide:

```text
What was detected?
Why was it detected?
Which evidence supports it?
Which reports contributed to the pattern?
```

# 34. Implemented Architecture (hardening pass)

> **LLM understands language. Safety structure drives the reasoning. MECHORA
> clusters safety mechanisms, not merely text.**

This section documents how the shipped system actually behaves. It is the
authoritative implementation reference for the hardening pass and supersedes
any earlier prose where the two disagree.

## 34.1 Non-negotiable concepts

- **Activity is context, not a hard boundary.** Two stories about different
  equipment and different activities ("flange tightening" and "pump overhaul")
  are the SAME precursor when the failed barrier, its state, the hazardous
  energy and the exposure mechanism are structurally identical. Activity is
  captured, shown and used only as context.
- **Barrier state is a closed, never-crossed set.** `verified`,
  `not_verified`, `failed`, `absent`, `partially_effective` and `unknown` are
  distinct canonical codes. They NEVER merge in grouping.
- **Hard grouping boundaries** (any one differing dimension blocks grouping):
  required barrier, barrier state, hazardous energy, **exposure mechanism**.
  Missing critical fields (`barrier`, `barrier_state`, `energy`, `exposure`)
  block confident grouping entirely — such observations go to NEEDS REVIEW.
- **A "precursor" is a failure story, not any report.** VERIFIED stories are
  held (`UNASSIGNED / PENDING REVIEW`) unless they form their own controlled
  family; they are never merged with failure stories or branded recurring.
- **Determinism.** The extraction + grouping pipeline is byte-repeatable: same
  narrative in, same canonical event, same evidence spans, same family id out.
  No Python hash-seed or iteration-order dependence.

## 34.2 Layers

| Layer | Responsibility | Implementation |
| --- | --- | --- |
| LANGUAGE | free narrative -> canonical codes + verbatim evidence spans | `App.rule_extractor`, `LLMExtractor`, `Canonicalizer`, `NegationEngine` |
| SAFETY | barrier state (authoritative), mechanical failure vs procedural omission, applicability guard | `NegationEngine`, `inferred_potential_consequence` |
| STRUCTURAL | clustering into mechanism families, WHY GROUPED / WHY NOT GROUPED | `PrecursorEngine`, `Clustering`, `Similarity`, `FamilyBuilder`, `Attention` |
| HSE | review flags, validation audit trail, attention signal | `SIFAssessor`, `LSRMapper`, `PATCH /observations/{id}/validation` |

## 34.3 Extraction & evidence grounding

- Canonical values carry a per-field provenance tag `field_basis`:
  `explicit` (a verbatim narrative span supports it), `inferred` (normalized or
  rule-derived, no direct quote) or `unknown`. Inferred values are never shown
  as if quoted.
- Evidence spans are always exact narrative substrings; a hyphenated synonym
  ("zero-energy") still resolves its exact spaced span ("zero energy").
- **Evidence attribution is provider-independent.** Whether the values came
  from the rules engine or from Gemini, `field_evidence` and `field_basis`
  (EXPLICIT/INFERRED/UNKNOWN) are recomputed deterministically from the
  canonical event against the ontology. The LLM may only propose values
  (language understanding); the pipeline decides whether real text supports
  them. A model-suggested exposure is never marked EXPLICIT when the narrative
  negates the release ("none was released"), and a negated non-event is never
  attached as positive evidence (`none` included in negated-outcome regexes).
- Potential consequence is **recomputed deterministically** from the final
  canonical hazard/exposure/state; an LLM can never invent one. It is labelled
  `model_inference` unless the narrative literally states the consequence
  (`explicit` with verbatim text). Actual consequence (injuries, releases) is
  populated ONLY from an explicit narrative statement; unstated -> `unknown`,
  never defaulted to "none".
- Negated outcomes ("no gas was released", "nothing leaked") are non-events and
  never become positive exposure/energy attributes.

## 34.4 Barrier-state engine (authoritative)

- "was not verified / not confirmed / skipped / not issued" -> `not_verified`.
- "ruptured / failed / blown" -> `failed`. "before X was verified" -> not_verified.
- "could not be verified" -> `unknown` (indeterminate, held for review).
- **"was NOT required / not needed / not necessary" -> `unknown`** (applicability,
  not a failure; never counted as a barrier-failure signal).
- "was not skipped" -> `verified` (the check was performed); "did not fail" ->
  `verified`. A negated outcome never masks a real control failure in the same
  sentence.

## 34.5 Precursor engine

- Signatures group only when barrier, barrier_state, energy AND exposure all
  match and every critical field is known. Connectivity is single-linkage
  through those hard boundaries — no merged pair in a family crosses a bound.
- Families expose `grouping_evidence` (WHY GROUPED, per dimension: same /
  mixed / distinct) and `exclusions` (WHY NOT GROUPED, with differing dimensions
  and basis) so every membership decision is explainable.
- `recurring` is explicit (`observation_count >= recurring_min_observations`).
  A single observation is never branded recurring.
- **Attention signal (0–100) is an explainable decision-support score, NOT a
  risk percentage and NOT a measure of injury likelihood.** It is computed from
  documented factors (recurrence, barrier failure, exposure severity, SIF
  evidence, cross-activity recurrence) and surfaces `attention_basis` +
  `attention_factors` with a disclaimer.

## 34.6 Extraction provider & provenance

- provider vocabulary is `rules` | `llm` | `auto` (back end and UI).
- Every analysis records `requested_provider` (what was asked), `provider` =
  `resolved_provider` (what actually ran) and, when an LLM pass was genuinely
  attempted and failed, `fallback_used` + `fallback_reason`. The UI shows a
  Fallback notice with the reason. Both response models expose
  `resolved_provider` alongside `provider`. An `auto` resolution to rules with
  no key-set is NOT a fallback.
- LLM failures (timeout, quota, malformed/extra JSON) degrade gracefully to the
  deterministic rules engine; no analysis is ever silently empty.

## 34.7 SIF & Life-Saving Rules

- SIF assessment is a decision-support prototype: it labels high/medium/low and
  NEEDS REVIEW with a basis and model note, NEVER a scientific risk score.
- IOGP Life-Saving Rules are mapped deterministically from barrier/energy/
  exposure and re-computed over the final canonical event (LLM-suggested rules
  are canonicalized and deduped first).

## 34.8 HSE human-in-the-loop

- `needs_review` + `missing_fields` flag under-specified observations at
  creation. Vague narratives are family `UNASSIGNED / PENDING REVIEW`.
- Validation PATCH accepts `status`, optional `reviewer` and `reason`, and
  records `validated_at` — an immutable audit trail. Fields surface
  `validation_reviewer`, `validation_reason`, `validated_at` in every payload.

## 34.9 Demo scenarios (verifiable via UI or API)

1. PTW-1 Pipeline flange / zero energy not verified / gas released.
2. PTW-2 Pump overhaul / no confirmation / gas escaped.
3. PTW-3 Valve maintenance / never checked / gas leaked.
4. PTW-4 Compressor service / skipped / gas released.
   -> ALL FOUR converge on one recurring family (PFAM-A7CC6, Energy Isolation
   Verification Failure). Different stories, same failed barrier, recurring.
5. PTW-5 Verified isolation -> separate, never merged, not recurring.
6. PTW-6 Isolation valve failure -> separate failed family.
7. PTW-7 Hot-work controls not verified -> separate family (different barrier
   + different exposure).
8. PTW-8 "Maintenance was performed on equipment." -> NEEDS REVIEW, all four
   critical fields missing, unassigned.

## 34.10 Validation & limits

- 126 automated tests pass (95 baseline + 21 hardening + 3 positive-
  verification precedence regression tests + 7 data-semantics regression
  tests), plus the frozen 216-record evaluation and the SIH-2026 negation
  critical suite.
- Frozen-eval acceptance thresholds all still hold (barrier_state 1.000,
  isolation verified/not-verified 1.000, hard-negative 1.000, family tag 0.972).
- Precedence rule (semantic regression fix): explicit un-negated positive
  verification ("Before opening the joint, isolation was verified, zero
  pressure confirmed, permits fully verified") resolves to VERIFIED and
  extinguishes consequence inference and SIF HIGH; order-violation
  constructions ("opened the drain before the line was proven depressurized")
  and negated forms ("NOT verified before", "NEVER confirmed before") remain
  NOT_VERIFIED.
- Data-semantics rules (consistency pass):
  - Verified/compliance groups (family_type "controlled") are NOT precursor
    families: excluded from /families, dashboard precursor & recurring
    counts, and recurring attention by default; still fetchable via
    ?include_controls=true or by family id for hard-negative validation.
  - One authoritative recurrence unit = unique observation/report records,
    used identically on the card, detail, threshold and linked-count surfaces;
    recurring status applies only to precursor families and only at
    count >= threshold, so impossible "1 ≥ 2" values never render.
  - Verified positive-control narratives without a release never infer an
    "Uncontrolled Gas Release" exposure; exposure/consequence stay Unknown
    unless explicitly grounded — enforced deterministically on BOTH the rules
    and LLM paths (an LLM-asserted release with no non-negated grounding
    span is extinguished; a genuinely grounded release survives).
  - Hard exclusion preserved: verified / not_verified / failed barrier
    states never share a family.
- Reproducibility: identical outputs verified across many Python hash seeds.
- Honest limits: SIF scoring is prototype-only; attention is NOT risk; MECHORA
  does not quantify OIL likelihood, does not predict accidents, and cannot
  replace a competent-person review. Grouping is structural; irony or tacit
  knowledge in a narrative is not parsed.
- Dev database is disposable and PostgreSQL-backed (local Postgres 18;
  role/db `mechora` provisioned, JSONB columns verified). Tests always run
  against their own temp SQLite file (conftest pins STORE=sqlite), so the
  suite stays hermetic without a live server.
- Observation ids are canonical and uniform: `OBS-<REPORT_ID>` (sanitised,
  deterministic). `create_observation` upserts by id/report_id, so re-analyzing
  the same report updates its record instead of creating a duplicate. Seed and
  API paths both use this id scheme; caller-supplied ids (tests) are preserved.
